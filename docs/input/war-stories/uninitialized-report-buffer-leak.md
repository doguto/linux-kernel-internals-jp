# 未初期化HIDレポートバッファによるカーネルメモリ漏洩 {#the-uninitialized-hid-report-buffer-kernel-memory-leak}

> 一語の修正（`kmalloc` は `kzalloc` であるべきだった）で、ヒープメモリの漏洩が塞がれた。フォレンジック機器メーカーはすでにこれを、実際に動作するスマートフォンのロック解除チェーンの一部に組み込んでいた。

収録
:   Linux、2024年10月（修正コミットの作成は2024-10-29。CVE-2024-50302はNVDが2024年11月に公開）

ドライバ
:   HIDコア（`drivers/hid/hid-core.c`）

報告者
:   Benoît Sevens（Google）

メカニズム
:   未初期化メモリの読み出し、`hid_alloc_report_buf()`

CVE-2024-50302 — CISA Known Exploited Vulnerabilitiesカタログ（2025年3月4日に追加）

*[事件簿: 入力/HIDのバグとリグレッション](../war-stories.md)の一部。*

## 事前の状態 {#before-state}

HIDデバイス（キーボード、ゲームパッド、タッチスクリーンなど、HIDプロトコルを話すあらゆるもの）は、レポートディスクリプタによって自身のデータ形式を記述する。カーネルはレポートの読み書きの前に、そのレポート1つ分を収めるサイズのバッファを割り当てる。`drivers/hid/hid-core.c` の `hid_alloc_report_buf()` がそのバッファを割り当てる関数である。これは送信側のレポート（ユーザー空間やドライバがLEDやフォースフィードバック効果を設定する場合）と、回線から受け取って解析する受信側のレポートの両方で使われる。

## きっかけ {#the-trigger}

`hid_alloc_report_buf()` は、素の `kmalloc()` でバッファを割り当てていた。`kmalloc()` は、そのページを以前使っていた何者かが残したままの状態のメモリを返し、ゼロクリアはしない。バッファが収めるようにサイズ決めされたレポートフィールドが実際には一度も書き込まれなかった場合（デバイスが切り詰められた、あるいは細工されたレポートを送ったため、またはレポート内のすべてのフィールドが埋まる前にコードパスがレポートを読み戻したため）、読み出しはゼロでもエラーでもなく、たまたまそのメモリを占めていたカーネルヒープの内容を返した。

## 観測された挙動 {#observed-behavior}

未初期化のレポートを読み出すと、それを消費する者（HID rawレポートインターフェース経由のユーザー空間、あるいは漏洩したバイトをさらに処理するドライバ）に古いカーネルヒープのデータが渡された。NVDはこれをCVSS 3.1で5.5（CWE-908、未初期化リソースの使用）と評価している。それ自体は単純な情報漏洩プリミティブである。この事件が注目に値するのは、単純なバグのメカニズムではなく、その使われ方である。CISAは2025年3月4日にCVE-2024-50302をKnown Exploited Vulnerabilitiesカタログに追加した。またAmnesty InternationalのSecurity Labは2025年2月にフォレンジックレポートを公開し、Google Threat Analysis Groupが少なくとも3つのゼロデイ脆弱性（CVE-2024-50302を含む）を特定したことを記録した。これらは、2024年12月にベオグラードで拘束された学生活動家のSamsung Galaxy A32のロック解除に使われたCellebriteのエクスプロイトチェーンの一部として悪用された可能性が高いとされる。Amnestyのレポート自身は、チェーンとハードウェアの帰属の両方について断定を避けている。「掲載された各デバイスが……成功したエクスプロイトチェーンの一部だったかどうかは不明である」とはっきり述べており、CellebriteのTurbo Linkアダプタについても「そのようなハードウェアベースの攻撃を容易にするために使われる可能性がある」ハードウェアとして説明しているだけで、一致が確認されたわけではない。単独では低深刻度に見えるカーネルの情報漏洩が、Googleの評価によれば、特定の人物に対して使われた実際のデバイスロック解除チェーンの1つの輪であった可能性が高い。たとえ完全なチェーンと正確なハードウェアが独立に確認されていないとしてもである。

## なぜ起きたか {#why-it-happened}

`kmalloc()` はアロケータ選択の既定の反射である。ゼロクリアを省くので `kzalloc()` より速く、読み戻す前にコードが完全に上書きしようとしているバッファであれば、それが正しい選択である。バグは、HIDのレポート処理を通るすべてのパスが「読む前に完全に書く」ことを保証しているわけではない点にある。デバイスは自身のディスクリプタが主張するより短いレポートを自由に送れるし、コードパスがこの特定のレポートでデバイスが一度も埋めなかったフィールドを読むこともありうる。その時点のバッファの内容は `kmalloc()` が返したものそのままである。攻撃者に影響されうるといっても、攻撃者（デバイス）が部分的に古い割り当てのうちどのバイトを要求させるかを制御できるという意味においてであり、それ以上に直接的な形ではない。修正は、HIDコアの多数のレポート処理パスのひとつひとつについて完全な初期化を監査・保証しようとするのではなく、すべてのレポートバッファを最初にゼロクリアする小さな一定のコストを受け入れる。

## 解決 {#resolution}

コミット `177f25d1292c` は、`hid_alloc_report_buf()` 内の唯一の割り当て呼び出しを `kmalloc(len, flags)` から `kzalloc(len, flags)` に変更する。修正はそれだけであり、他のロジックの変更はない。

## 教訓 {#what-it-taught-us}

**未初期化メモリのバグが危険になるのに、巧妙なトリガーは必要ない。必要なのは、それをより大きなチェーンの一片として使おうとする現実の行為者である。** このバグのメカニズムには何も珍しいところはない。カーネル全体で見られる「読む前に完全に書かれると仮定したが、その仮定が常に成り立つわけではない」というパターンと同じである。フォレンジックレポートに値するものにしたのは目新しさではなく、商用のデバイスロック解除製品が修正の出荷前にこれを発見し武器化していた可能性が高い、とGoogleが評価したことだった。

**1行の低リスクな修正（`kmalloc` → `kzalloc`）で、大半の監査では軽微と評価されるバグを塞げる。それが一部をなしていたエクスプロイトチェーンを誰かに見せられるまでは。** 孤立したプリミティブの深刻度と、他のバグと組み合わさったときにそれが可能にするものの深刻度は別の問題であり、HIDコアを単独で監査している防御側が、前者から後者を必ずしも見抜けるとは限らない。

!!! warning "注意すべきパターン"
    ゼロクリアしないアロケータで割り当てたバッファを、割り当て以降すべてのバイトが書き込まれたことを先に証明しないコードパスで読み戻している。特に、バッファを埋めるものが攻撃者の影響を受け（この場合はデバイス自身のレポート長）、バッファの全サイズより正当に短くなりうる場合に注意すること。
