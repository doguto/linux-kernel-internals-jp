# USBの事件簿 {#usb-war-stories}

> 2つの事実に行き着く6つの事件: USBは*信頼できない物理デバイス*がカーネルに解析すべき複雑なデータを渡すバスであること、そしてUSBのホットプラグモデルのために、すべてのコードパスが操作の途中でデバイスが足元から消えることに耐えなければならないこと

USBの利便性 — 自己記述的なデバイス、ホットプラグ、デバイスが名乗るIDに基づくドライバの自動ロード — は諸刃の剣である。以下の最初の3つの話は、その信頼が悪用された例である。デバイスが自分の正体について嘘をついたり、本物のデバイスなら決して送らないような入力を[ディスクリプタ](enumeration.md)パーサに与えたりする。最後の3つは同じコインの裏側である。ホットプラグとは、デバイス（あるいはガジェットモードではホスト）が操作の途中で消えうることを意味し、それに手を伸ばすすべてのコードパスはその消失に耐えなければならない — 悪意ある入力は必要なく、タイミングが悪いだけで十分である。

## 1. BadUSB: 自分の正体について嘘をつくデバイス（2014年） {#1-badusb-the-device-that-lies-about-what-it-is-2014}

USBの識別情報は**自己申告**である。デバイスの物理的な形態と、それが提示するディスクリプタとを結び付けるものは何もない。フラッシュドライブが「私はマスストレージだ」と言うのは、単にそのファームウェアがそう選んでいるからにすぎない。Black Hat 2014で実演されたBadUSBはこれを武器にした。普通のUSBメモリのコントローラを書き換えて、ストレージである*のに加えて*、**HIDキーボード**を名乗る2つ目のインターフェースを列挙させる — そして接続された瞬間に、マシンにコマンドを「タイプ」するのである。カーネルの何かが悪用されたわけではない。カーネルはUSBが定めるとおりのことを正確に行った。脆弱性はまさに信頼モデル*そのもの*だったのである。

「USBはデバイスを信頼する」ことに対するパッチは存在しないので、カーネルの答えは**修正ではなくポリシー**である。すべてのUSBデバイスはsysfsに`authorized`フラグを持ち、`authorized_default`を設定すると、新たに接続されたデバイスは**人間が承認するまで非認可**となる — カーネルはそれらを列挙はするが、ドライバはバインドしない。USBGuard（デバイスの識別情報による許可リスト）のようなユーザー空間ツールと組み合わせることで、ロックダウンされたマシンは突然現れたキーボードを拒否できる。カーネルの[USB authorization](https://docs.kernel.org/usb/authorization.html)ドキュメントを参照のこと。

**教訓:** 識別情報が自己申告である場合、*認証*はバスより上の層に置かなければならない。カーネルには本物のキーボードと悪意あるキーボードを区別できないので、ポリシー層が判断するための制御手段を公開するのである。

## 2. CVE-2016-2384: 二重に解放するMIDIディスクリプタ {#2-cve-2016-2384-a-midi-descriptor-that-frees-twice}

デバイスが危険であるためにキー入力を注入する必要はない — *ありえない*形で自身を記述するだけでよい。CVE-2016-2384は、USB-MIDIドライバ（`snd-usbmidi`）における**double-free**だった。ドライバのセットアップパスが拒否するようなUSB-MIDIインターフェースディスクリプタをデバイスが提示すると、エラーパスが`umidi`オブジェクトを解放し — さらに2つ目のクリーンアップパスがそれを再び解放した。細工されたディスクリプタ（BadUSBのものを含め、任意の物理デバイスから送り込める）によって、これは典型的なdouble-freeとなり、アロケータを破壊してコード実行への扉を開いた。

修正（[`07d86ca93db7`](https://git.kernel.org/linus/07d86ca93db7) "ALSA: usb-audio: avoid freeing umidi object twice"）は、重複した解放を単に取り除いただけだった。しかし重要なのはバグの*クラス*である — ディスクリプタパーサのエラーパスが、攻撃者が形作った入力を誤って扱うというものだ。このパーサは、ディスクリプタが協力的なハードウェアから来ることを前提に書かれていた。

**教訓:** ディスクリプタパーサは攻撃対象領域のパーサである。ディスクリプタ内のあらゆるカウント、長さ、エンドポイント番号は攻撃者が制御でき、（本物のデバイスではめったに通らない）エラーパスこそがバグの潜む場所である。

## 3. デバイス側からホストをファジングする: raw-gadgetとsyzkaller {#3-fuzzing-the-host-from-the-device-side-raw-gadget-and-syzkaller}

USBの歴史の大半において、ホストスタックは事実上ファジング不可能だった — テストするには本物の悪意あるハードウェアが必要だったのである。それが変わったのは、カーネルがUSBデバイスをソフトウェアで*エミュレート*する能力を得たときだった。**`dummy_hcd`**は仮想デバイスコントローラにつながった仮想ホストコントローラを提供し、**raw-gadget**はユーザー空間のプログラムがそのデバイス側をバイト単位で駆動し、好きな*任意の*ディスクリプタと応答を提示できるようにする。Andrey Konovalovはこれを**syzkaller**に組み込み、完全に攻撃者が制御する「デバイス」をホストスタックに接続できるようになったファザーは、USBドライバ全体で**数百**のバグを発見した: 切り詰められたディスクリプタでの範囲外読み取り、切断時の競合によるuse-after-free、長さチェックの欠落などである。

その結果、USBコアとドライバ全体にわたって体系的な堅牢化の波が起きた — 代表的なコミットは[`2e1c42391ff2`](https://git.kernel.org/linus/2e1c42391ff2) "USB: core: harden cdc_parse_cdc_header"である — ファジングできるようになるまで、誰もそれらのパーサに不正な入力を与えたことがなかったために欠けていた長さチェックと境界チェックが追加された。[raw-gadget](https://docs.kernel.org/usb/raw-gadget.html)のドキュメントを参照のこと。

**教訓:** パーサが脆弱だった理由は、そのまま修正された理由でもある — 何十年もの間、ホストに不正なディスクリプタを送る唯一の方法は特殊なハードウェアだったので、そのパスはテストされないままだった。*デバイス*側をプログラム可能にしたことで、到達不能だった攻撃対象領域がファジング可能なものに変わったのである。

## 4. CVE-2024-36896: sysfsが問い合わせ中のハブを抜く {#4-cve-2024-36896-unplugging-a-hub-while-sysfs-is-asking-it-a-question}

USBハブはポートごとの制御をsysfs経由で公開しており、その中にはユーザー空間が個々のポートの電源を落とせる`disable`属性（`drivers/usb/core/port.c`）がある。これを読み書きするには、ポートデバイスからそれを所有するハブへとたどる必要がある: `hdev = to_usb_device(dev->parent->parent)`、続いて`hub = usb_hub_to_struct_hub(hdev)`である。

`usb_hub_to_struct_hub()`は`NULL`を返すことがある — まさにハブが削除処理の途中にあるときに、そうなる。`disable_show()`と`disable_store()`はどちらもそのチェックを省略して、すぐに`hub->intfdev`を参照外ししていた。生きているポートから見つかったハブデバイスなら、その背後にハブ構造体がまだ存在するはずだと仮定していたのである。KASANとsyzkallerが、その結果生じるアクセス違反を発見した。`disable`のsysfs読み書きが進行中の瞬間にハブ（またはその親）を抜くと、ハンドラがNULLポインタを参照外しする。このバグは、`disable`属性そのものが追加されたLinux 6.0から存在していた。

修正（[`a4b46d450c49`](https://git.kernel.org/linus/a4b46d450c49) "USB: core: Fix access violation during port device removal"、Alan Stern、6.9でマージ）は、欠けていた`if (!hub) return -ENODEV;`チェックを両方のハンドラに追加し — ついでに`hub->intfdev`の参照外しを`dev->parent`に置き換えた。これは`hub`がまだ存在している必要なしに、同じインターフェースデバイスに到達できる。

**教訓:** デバイスの親階層をたどるsysfsハンドラは、その構造上、ホットアンプラグと競合している — ルックアップと参照外しの間に、たどった先のデバイスが破棄されることを防ぐものは何もない。可能であれば、2つ目のオブジェクトがまだ生きていることに依存するポインタではなく、ルックアップよりも長く生存することが保証されたポインタ（ここでの`dev->parent`のような）を通じてデータに到達すること。

## 5. CVE-2026-80824: usbfsがデバイスを解放し、それでもなおそれを通して読む {#5-cve-2026-80824-usbfs-frees-the-device-then-reads-through-it-anyway}

`usbfs`は、ユーザー空間が`/dev/bus/usb/*`ノードに対してUSBリクエスト（URB）を直接投入・回収できるようにするもので、ゼロコピー転送のための`mmap()`ベースのバッファも含む。プログラムがusbfsのファイルディスクリプタをクローズすると、`usbdev_release()`がすべてを片付ける。`usb_put_dev(dev)`を呼んで`struct usb_device`への参照を落とし、それから完了した非同期URBのリストをたどって、それぞれを`free_async()`で解放する。

`mmap()`ベースのURBにとって、この順序は逆である。`free_async()`は、バッファがusbfsのmmap領域から来たURBについて`dec_usb_memory_use_count()`を呼び、その関数の最初の文は`ps->dev->bus`を参照外しする — つまり、`usbdev_release()`がたった今解放したまさにその`usb_device`を通して読み戻すのである。usbfsの参照がたまたまデバイスの最後の参照だった場合 — 修正コミットによれば、切断の直後にはそうなりうる — `usb_put_dev()`はすでにそれを解放しており、ドレインループは解放済み構造体のメモリを読んで、それを`struct usb_hcd *`としてたどってしまう。

これは狭い競合ウィンドウではない — 毎回再現する。生きている`MAP_SHARED`マッピングはオープンされたファイルへの独自の参照を保持するので、usbfsのfdのマッピングがすべてなくなるまで`usbdev_release()`は実行すらされない。そしてそれが実行される時点では、`dec_usb_memory_use_count()`の解放する側の分岐を通ることが保証されている。`/dev/bus/usb`ノードへの読み書きアクセス権を持つ非特権プロセスは、これを決定的にトリガーできる: fdを`mmap()`し、マッピング内のバッファを使ってURBを1つ投入し、デバイスが抜かれるのを待ってから、`munmap()`と`close()`を行えばよい。

修正（[`0dd68b5d01d0`](https://git.kernel.org/linus/0dd68b5d01d0) "usb: usbfs: fix use-after-free of usb_device in usbdev_release()"、Miguel Peñaranda、7.3でマージ）は、2つのステップを単に並べ替えたものである。まず完了したURBをドレインして解放し、その後で`usb_put_dev()`を呼ぶ。元の2つのステップの間にあるものは何も、参照がすでに落とされていることを必要としていなかった。

**教訓:** 「参照を落としてから、それに依存していたものを片付ける」という順序は、クリーンアップパスがその参照が守っていたオブジェクトを通して読み戻しうる場合には常に逆である。このバグはLinux 4.6でmmapゼロコピー機能が追加されて以来存在していた — その10年間、この順序が問題になるのは、プログラムがまさにこの方法で処理の途中に切断された場合だけだったのである。

## 6. CVE-2025-68282: 最初の修正では塞げなかった競合をteardownフラグが塞ぐ {#6-cve-2025-68282-a-teardown-flag-closes-a-race-its-first-fix-didnt}

USBガジェットデバイス（カーネルがホストではなくUSB *デバイス*として動作するもの — [ガジェットの内部](xhci-gadget.md)を参照）は、状態変化（`configured`、`suspended`など）を`sysfs_notify()`呼び出しで通知する。この呼び出しは、状態変化を引き起こしたアトミックコンテキストで実行されないよう、workqueue（`gadget->work`）に遅延される。`usb_del_gadget()`はガジェットを破棄する。その途中で`flush_work()`を呼んで保留中の`gadget->work`の完了を待ち、それからガジェットのメモリを解放する。

このコードの最初のバージョンには、「無関係な何らかの並行イベント」よりも微妙な競合があった。`device_del()`自体が、新たな`gadget->work`を同期的にスケジュールしうるのである。修正コミットは実際の呼び出しチェーンの1つを追跡している: `device_del() → gadget_unbind_driver() → usb_gadget_disconnect_locked() → dwc3_gadget_pullup() → dwc3_gadget_soft_disconnect() → usb_gadget_set_state() → schedule_work()`。`flush_work()`が`device_del()`の*前*に実行されると、そのワークアイテム — 外部の何かではなく、破棄処理そのものによってスケジュールされたもの — は、まもなく解放されるメモリを指したまま残された。[`399a45e5237c`](https://git.kernel.org/linus/399a45e5237c)（"usb: gadget: core: flush gadget workqueue after device removal"）はまさにそれを修正した。`flush_work()`を`device_del()`の*後*に移し、`device_del()`自身が引き起こすワークもドレインされるようにしたのである。KASANは、これがウィンドウを狭めただけで閉じてはいないことを発見した。本当に別個の並行イベントが、（移動後の）`flush_work()`呼び出しとガジェットのメモリが実際に解放されるまでの間に新たなワークアイテムをスケジュールすることがまだ可能で、まったく同じuse-after-freeを再現したのである。

本当の修正（[`baeb66fbd420`](https://git.kernel.org/linus/baeb66fbd420) "usb: gadget: udc: fix use-after-free in usb_gadget_state_work"、Jimmy Hu（Google）、6.18でマージ）は、最初の試みに欠けていたものを追加した: `usb_gadget`上の`teardown`フラグと`state_lock` spinlockである。`usb_del_gadget()`は`flush_work()`を呼ぶ*前*にロックを取ってフラグを立て、ワークをスケジュールする唯一の場所である`usb_gadget_set_state()`は、何かをキューに入れる前に同じロックの下でフラグを確認する。2つの操作の互いの順序を整える（フラッシュを後ろに移す）ことで1つのウィンドウは閉じた。両側が共有するロックの下で確認されるフラグは、順序に関係なくすべてのウィンドウを閉じる。

**教訓:** 「クリーンアップが終わったと思った後で何かがスケジュールされた」ことに起因するuse-after-freeには、通常、クリーンアップのタイミングを並べ替えることではなく、スケジュールする側が使うのと同じロックで守られた状態チェックが必要である — 並べ替えは競合を狭め、共有されたガード付きフラグは競合を閉じる。根本的なバグはLinux 3.12にまで遡り、最初の不完全な修正の試みでさえ、バグの混入から10年以上経ってから出荷された。
