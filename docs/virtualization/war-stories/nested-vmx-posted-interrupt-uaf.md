# エラーパスで1つのフィールドを忘れた Nested-VMX のリファクタリング {#the-nested-vmx-refactor-that-forgot-one-field-on-the-error-path}

> CVE-2018-16882 — 些細なラッパー関数を削除したことで、posted interrupt のセットアップパスが失敗時の早期リターンを中心に再構成され、その早期リターンは、以前は呼び出しのたびに無条件にリセットされていたポインタのリセットを飛ばしてしまった。ポインタはそのままダングリングし、後の use-after-free に直結した

## 事前の状態 {#before-state}

ネストされた仮想化では、L0（本物のハイパーバイザ）が L1（それ自体がハイパーバイザであるゲスト）を実行し、L1 がさらに L2（L1 自身のゲスト）を実行する。L1 が本物の VMX ハードウェアに触れることはない — L0 が L1 の VMX 命令をインターセプトし、L1 が意図する VMCS の状態を `vmcs12` としてシャドウし、それから `vmcs12` を L0 自身に必要な制御とマージして、実際にハードウェアにロードされる VMCS（`vmcs02`）を構築する。posted interrupt は、小さなメモリ上の posted-interrupt ディスクリプタを介して、物理 CPU が VM exit を強制することなく実行中の vCPU に割り込みを配送できるようにするハードウェア機能である。ネストされた L2 ゲストについては、L0 は L2 のための *L1 の* posted-interrupt ディスクリプタ — L1 が `vmcs12->posted_intr_desc_addr` に指定するゲスト物理アドレス — を追跡しなければならない。これは、その GPA を本物のホスト page に変換し、ピン留めし、L0 が直接参照できるカーネルポインタ `vmx->nested.pi_desc` に `kmap()` することを意味する。

`nested_get_vmcs12_pages()` はネストされた VM-entry のセットアップのたびにこの変換を行い、以前の呼び出しからキャッシュされたマッピングがあれば、先に*以前の*マッピングを解放しなければならない。

## きっかけ {#the-trigger}

`5e2f30b756a37`（"KVM: nVMX: get rid of nested_get_page()"）は薄いラッパー関数を削除し、その置き換えをインライン化した — 見た目の上では純粋なクリーンアップである。しかしその削除は、途中で posted interrupt ブロックの制御フローを再構成していた。変更前は、`vmx->nested.pi_desc_page` と `vmx->nested.pi_desc` は呼び出しのたびに無条件に再代入されていた — 代入は成功かどうかにかかわらず行われたので、検索が失敗すると両方とも `NULL` になった。変更後、コードは失敗時の早期リターンを中心に書き直された。`page = kvm_vcpu_gpa_to_page(...); if (is_error_page(page)) return;` — そしてフィールドへの代入はそのチェックの*後*に移された。失敗時、関数は `pi_desc_page` にも `pi_desc` にも一切触れずに戻るようになり、以前の成功した呼び出しからキャッシュされていた値がそのまま残る。関数冒頭の「起こるはずのない」クリーンアップブロックは、古い page を解放するときに `pi_desc_page` を `NULL` にリセットする — しかし `pi_desc` はリセットしておらず、それはたった今 `kunmap()` されて解放された page をまだ指している。

## 観測された挙動 {#observed-behavior}

修正自身のコミットメッセージには、作者が使った正確な再現手順が記されている。有効な posted-interrupt ディスクリプタアドレスと無効な `MSR_EFER` を指定して `vmlaunch` を呼ぶ。すると `nested_get_vmcs12_pages()` がマップした `pi_desc_page`/`pi_desc` をキャッシュした後で、検証の後段で無効な EFER のために vmlaunch 全体が失敗する。もう一度 `vmlaunch` を呼ぶ。今度は有効な EFER と、意図的に無効にした `posted_intr_desc_addr` を指定する — これは「起こるはずのない」ブロックを起動し、以前キャッシュされた page をアンマップして解放し、`pi_desc_page` を `NULL` にリセットするが、続く新しいアドレスの検索も失敗し、関数は `pi_desc` に一度も触れずに早期リターンする。この時点で `vmx->nested.pi_desc` は解放済みメモリを指すダングリングポインタであり、L0 自身の VMCS 内のハードウェア VMCS フィールド `POSTED_INTR_DESC_ADDR` は解放された物理 page をまだ指している — しかし何も派手に失敗していないので、`vmlaunch` は先へ進む。L2 ゲストのコードからプロセッサ間割り込みを発行すると、`vmx_complete_nested_posted_interrupt()` が `pi_test_and_clear_on(vmx->nested.pi_desc)` を呼び、ダングリングポインタを直接参照する — ネストされた仮想化と APIC 仮想化の両方が有効で、ホスト CPU が posted interrupt をサポートしていればいつでも到達可能な、ゲストから起動できるホストカーネルの use-after-free である。

## なぜ起きたか {#why-it-happened}

ラッパーを削除したコミットの diff は、1行ずつ読むと何の変哲もないクリーンアップに見える — ヘルパー関数がインライン化され、`NULL` の戻り値に頼る代わりに各呼び出し箇所に明示的なエラーチェックが追加された。diff の中に状態管理の変更に見えるものは何もない。しかし、「常に代入する、ときには null を」という構造を「成功パスでのみ代入し、そうでなければ早期リターンする」に作り替えたことで、周囲のコードが依存していた、失敗時に暗黙にリセットするという振る舞いが、ひっそりと取り除かれた — ブロックが責任を持っていた2つのフィールドの両方ではなく、片方について。リファクタリングの作者には、これが機械的な変更だと信じる十分な理由があった。バグは、古いコードの無条件代入の構造が黙って保証していたが、新しい早期リターンの構造はもはや保証しなくなったものの中にある。

## 解決 {#resolution}

`c2dd5146e9fe1`（"KVM: Fix UAF in nested posted interrupt processing"）は、「起こるはずのない」ブロックに欠けていたちょうど2行を追加する。`pi_desc_page` と並んで `vmx->nested.pi_desc` を `NULL` にリセットし、動作中のハードウェア VMCS フィールド `POSTED_INTR_DESC_ADDR` を無効な番兵値（`-1ull`）にリセットして、ソフトウェアのポインタもハードウェアの posted interrupt 機構も解放された page を参照できないようにする。これでソフトウェアとハードウェアの両方の状態が、古いマッピングが取り壊されるまさにその時点で整合させられ、2つのうち一方が中途半端に更新されたまま残ることはなくなった。

## 得られた教訓 {#what-it-taught-us}

**制御フローを変えるリファクタリング — 早期リターンかフォールスルーか — は、個々の行の変更が単体ではすべて正しく見えても、暗黙の不変条件を黙って落としうる。** 古いコードの「常に代入する、null であっても」というパターンは二重の役割を果たしていた。成功時には使える値を生成し、失敗時には古い状態をリセットする。どちらも同じ無条件代入の副作用としてである。新しいコードはそれを「成功時にのみ代入する」に分割したが、失敗時にリセットする振る舞いを明示的に保持する必要があることを、誰も導き直さなかった。

**クリーンアップブロックが複数の関連する状態の解放に責任を持つとき、その一部だけをリセットするのは、何もリセットしないより悪い — 正しく見えてしまうからである。** 「起こるはずのない」ブロックは `pi_desc_page` を*確かに*リセットしていた。その部分的な正しさこそが、このバグをコードレビューで隠れさせたものである。「解放は元に戻されたか」を探して読み流すレビュアーは、page の参照がクリアされているのを見て先へ進み、その page から導出されたポインタが一緒にクリアされていないことに気付かない。

!!! warning "注意すべきパターン"
    2つ以上のフィールドが常に互いに整合していることになっている場合（ここでは、page の参照と、その page からマップされたポインタ、さらに同じアドレスを反映するハードウェアレジスタ）、エラー時にその1つをリセットするコードパスは、すべてをリセットする必要がある — そして、リセットが行われる*タイミング*を変えるリファクタリング（無条件代入か早期リターンか）は、リファクタリングの作者が念頭に置いていたものだけでなく、古い制御フローが暗黙に維持していたすべての不変条件に照らしてチェックされる必要がある。
