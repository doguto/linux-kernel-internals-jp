# vhost：長さゼロのディスクリプタを忘れていたダーティログカウンタ {#vhost-the-dirty-log-counter-that-forgot-zero-length-descriptors}

> CVE-2019-14835 — vhostのライブマイグレーション用ダーティページロギングは、ディスクリプタごとに1つのログエントリなのだから、ログの数がディスクリプタの数そのものを追い越すことはありえないと仮定していた。この不変条件は、ゲストが渡す長さゼロのディスクリプタ1つで破ることができ、日常的なマイグレーションがゲストに制御されたカーネルヒープオーバーフローへと変わった

公開日
:   2019年9月17日（Tencent Blade Team、oss-security経由の協調的開示）

報告者
:   Peter Pi、Tencent Blade Team

CVSS
:   NVDでは7.8 HIGH（`CVSS:3.1/AV:L/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:H`）。Red Hat独自のスコアでは7.2 HIGH（`CVSS:3.0/AV:L/AC:H/PR:H/UI:R/S:C/C:H/I:H/A:H`）— 2つのCNAは攻撃の複雑さと必要な特権について見解が分かれている

バグの混入時期
:   commit `3a4d5c94e959`、vhost_netの最初の導入、2010年1月

## 事前の状態 {#before-state}

vhostはvirtioデバイスのエミュレーションをホストカーネル内に移す — virtqueueの通知のたびにユーザー空間のQEMUへトラップするのではなく、`vhost_net.ko` がリングを直接処理し、コストの高いユーザー空間への往復をホットパスから取り除く。ライブマイグレーション中、QEMUはどのゲスト物理pageがvirtqueue操作によって触られたかを知る必要がある。そうすれば前回のパス以降に変化したpageだけを正確に再送できる。vhostはこれをサポートするため、マイグレーション用のダーティトラッキング（`VHOST_F_LOG_ALL`）がネゴシエートされている場合、ディスクリプタのアドレスを固定サイズのカーネル配列（`vq->log`。`dev->iov_limit` 個のエントリ分のサイズで、vhost-netでは1088）に記録する。

`get_indirect()` と `vhost_get_vq_desc()` にあるロギングコードは、明文化されていない1つの不変条件に依存していた。`log_num`（固定サイズのログ配列に書き込まれたエントリ数）は `in_num`（ゲストが書き込み可能なディスクリプタについて生成されたiovecセグメント数）を決して超えない、というものである — 2つのカウンタは1ディスクリプタずつ歩調を合わせて進むはずだったからである。`in_num` は呼び出し元のiovec配列のサイズに対してすでに境界チェックされていた。`log_num` 自体は一度も境界チェックされなかった。それが必要になるはずがなかったからである。

## きっかけ {#the-trigger}

`translate_desc()` は長さゼロのディスクリプタに対して `ret = 0` を返す — その中核のコピーループ `while ((u64)len > s)` は、`len` がゼロのとき一度も実行されないからである。修正前のロギングコードは、この戻り値を額面どおりに受け取っていた。`*in_num += ret;`（ゼロを足すので `in_num` は進まない）の後に、無条件で `if (unlikely(log)) { log[*log_num].addr = ...; log[*log_num].len = ...; ++*log_num; }` が続く — `ret` がゼロであるかどうかにかかわらず、ログエントリが書き込まれ `log_num` が進む。ゲストが渡す、書き込みフラグ付きで長さゼロのディスクリプタ1つで、配列サイズの保護が依存していた「log_numはin_numに追従する」という不変条件が破られる。`log_num` は `in_num` を追い越して進めるようになり、コード中にそれを直接制限するものは他に何もない。

## 観測された挙動 {#observed-behavior}

増幅は間接ディスクリプタテーブルから生じる。ゲストは最大65,536エントリ（制限は `count > USHRT_MAX + 1` だけ）を持つ間接テーブルを渡すことができ、その各エントリを書き込みフラグ付きで長さゼロのディスクリプタにできる。ループの各反復は、攻撃者が制御する8バイトのゲスト物理アドレスを `log[log_num]` に書き込み、何の制限もなく `log_num` を進める — そのため最初のおよそ1,088エントリを過ぎると、書き込みは `kmalloc_array` で割り当てられたログバッファの末尾をそのまま越えて続き、場合によっては数万個の16バイトエントリにわたって、攻撃者が制御する内容がバッファの後ろのカーネルヒープメモリに順番に書き込まれていく。Tencent Blade Team自身の開示は、同一の呼び出しパス `handle_rx() → get_rx_bufs() → vhost_get_vq_desc() → get_indirect()` を独立にたどっており、注釈付きのソース抜粋で同じ行を指摘している。"log buffer overflow, because log_num can be USHRT_MAX, but log buffer size is far below than USHRT_MAX."（訳: ログバッファのオーバーフロー。log_numはUSHRT_MAXになりうるが、ログバッファのサイズはUSHRT_MAXよりはるかに小さい）。脆弱なパスは `VHOST_F_LOG_ALL` がネゴシエートされているときにしか実行されないので、これは明確にマイグレーション時のバグである — すぐにパッチを当てられない管理者向けのRed Hat自身のガイダンスは、暫定的な緩和策として、ゲストのライブマイグレーションを無効にするか、`vhost_net` モジュールを丸ごとブラックリストに入れることだった。

## なぜ起きたか {#why-it-happened}

「ディスクリプタごとに1つのログエントリなので、log_numは決してin_numを追い越さない」という不変条件は、通常のディスクリプタすべてについて構造上成り立っていた — 長さが非ゼロのディスクリプタは必ず少なくとも1つのiovecセグメントを生成し、両方のカウンタを一緒にインクリメントする。長さゼロのディスクリプタは仕様で許された正当な値だが、ロギングコードにとっては別途扱う価値のあるケースとして思い浮かばなかった。ディスクリプタ変換ロジックの観点からは完全なno-opだからである。コピーするデータも、記録するものもない。バグの本質は、「記録するものがない」と「何も記録しない」が2つの別々の判断であり、そのうち一方しか実際には実装されていなかったことにある — コードは*コピー*する価値のあるものはないと判断したが、それでもなお無条件にログエントリを記録していた。

## 解決 {#resolution}

`060423bfdee3f`（"vhost: make sure log_num < in_num"）は、`get_indirect()` と `vhost_get_vq_desc()` の両方での2語の変更でこの穴を塞ぐ。ロギングの条件を `if (unlikely(log))` から `if (unlikely(log && ret))` に変えるのである — ログエントリは、ディスクリプタが実際に長さ非ゼロのiovecセグメントを生成した場合（`ret != 0`）にのみ書き込まれるようになり、残りのコードがすでに前提としていた「log_numはin_numに追従する」という不変条件が回復される。コミットメッセージの言葉では、"There's no need to log when desc.len = 0, so just don't increment log_num in this case."（訳: desc.len = 0のときはログを取る必要がないので、この場合は単にlog_numをインクリメントしない）。

## 教訓 {#what-it-taught-us}

**一般的なケースで「構造上」成り立つ不変条件であっても、それに依存するコードが独立に検証できない場所では、明示的にチェックする必要がある。** `log_num <= in_num` を信頼していたすべてのコードパスには、そう信じるだけの十分な理由があった — 正当でありふれた入力値（長さゼロのディスクリプタ）が、不変条件の元々の論理が実際にはカバーしていないケースだと判明するまでは。

**境界チェックされたカウンタと「歩調を合わせて進むはず」のカウンタは、たとえそう見えても、それ自体が境界チェックされているわけではない。** `in_num` が保護されていたのは、出力先のiovec配列のサイズに対して直接チェックされていたからである。`log_num` がその保護を受け継いでいたのは、2つのカウンタが乖離しえないと開発者が仮定していたという意味においてだけだった — その仮定は9年間正しかったが、たった1つのエッジケースの入力によって、実際にはどこでも強制されていなかったことが示された。

!!! warning "注意すべきパターン"
    2つのカウンタが1対1で互いに追従することになっていて、一方にしか明示的な境界チェックがない場合、チェックされている方を進めずに、チェックされていない方を進められる入力は何かを問うこと。長さゼロのバッファ、空文字列、no-op の反復 — 「何も起きなかった」ケースこそ、暗黙の歩調合わせの不変条件が一度も実際には強制されていなかった可能性が最も高い場所である。
