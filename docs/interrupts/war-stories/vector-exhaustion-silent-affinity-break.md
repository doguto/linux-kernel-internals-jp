# ベクタ空間が黙ってアフィニティを壊していたことを示す警告 {#the-warning-that-vector-space-was-silently-breaking-affinity}

> 管理者が、CPUアフィニティを予約済みの割り込みを有効化する。ところが希望していたCPUはその後ベクタを使い果たしていたため、カーネルは動作させるために黙ってアフィニティを広げる。そして約2年間、それが起きたことをsyslogから知る方法はなかった

収録
:   Linux 5.4（2019年11月）· 修正の作成は2019年8月22日

作者
:   Neil Horman（修正）。Red Hat関係の報告者が報告・テスト（コミットの `Reported-by`/`Tested-by` タグによれば `djuran@redhat.com`）

CVEではない

*[事件簿: 割り込みとIRQアフィニティのバグ](../war-stories.md)の一部。*

## 事前の状態 {#before-state}

x86の各CPUには合計256個の割り込みベクタがあるが、その大半はデバイスには使えない。32個はCPUの例外とトラップのためにアーキテクチャが予約しており、さらに22個をカーネル自身がIPIやローカルAPICタイマーなどの内部用途に予約している。残る202個が、CPUごとにデバイス割り込みへ実際に割り当てられるベクタである。割り込みがセットアップされるとき、あるいはカーネルや管理者がそのアフィニティを変更するとき、ベクタ割り当てコードは要求されたアフィニティマスク内のいずれかのCPU上で空きベクタを割り当てることで、そのマスクを尊重しようとする。

## きっかけ {#the-trigger}

割り込み数の多いデバイスを多数抱えるシステム（コア数の多いマシン上のマルチキューNICやストレージコントローラがよくある例）では、要求されたアフィニティマスク内のすべてのCPUが、割り当て可能な202個のベクタをすでにすべて使っていることも十分にありうる。この特定の障害モードは `activate_reserved()` にある。これは、アフィニティが即座に割り当てられるのではなく*予約*されていた割り込みについて、ベクタ割り当てを確定させる関数であり、2017年9月のx86ベクタ管理の再設計（Linux 4.15）で導入されたパスである。有効化の際に予約マスク内のすべてのCPUでベクタが尽きていると判明した場合、`assign_irq_vector_any_locked()` はリクエストを失敗させない。予約されていたものより外側の、より広いCPU集合へ黙ってフォールバックし、代わりにそこへ割り込みを割り当てる。（この再設計以前の古いベクタ割り当てコードは、同等の状況で黙ってマスクを広げるのではなく `-ENOSPC` を返していた。）

## 観測された挙動 {#observed-behavior}

実際に有効なアフィニティは `/proc/irq/$N/effective_affinity` から読めた。これはこの修正の約2年前、Linux 4.13で追加されたファイルである。しかしフォールバックが起きてもカーネルログには何も書かれなかったため、予約されたアフィニティが黙って広げられたことを示すものは何もなかった。すでにアクティブな割り込みについては、アロケータが尊重できない場合、`/proc/irq/$N/smp_affinity` を通じた新しいアフィニティの書き込みは `-ENOSPC` で目に見える形で失敗する。黙って起こるのは、特に*予約モード*の有効化パスの場合である。レイテンシに敏感なワークロードやNUMAを意識したワークロードのために割り込みを固定している管理者は、デバイスを有効化してもエラーを目にせず、`effective_affinity` を自分が要求したものと照合しに行く理由もなかった。「固定した」ワークロードの性能が期待どおりにならなくなって初めて気づくが、その時点でその不一致をシステムの別の場所でのベクタ枯渇まで追跡するには、すでにこの特定の障害モードを疑っている必要があった。修正の `Reported-by`/`Tested-by` タグは、これに遭遇し修正を検証した実在の報告者の功績を記しているが、変更履歴には彼らの正確なワークロードは書かれていない。

## なぜ起きたか {#why-it-happened}

これは誤った挙動という意味でのバグではない。フォールバック自体はおそらく正しい振る舞いである。割り込みの配送を完全に拒否するのは、要求された集合の外のCPUで配送するよりも悪いからだ。欠けていたのは純粋に可観測性だった。コードパスが設計どおりに正確に機能していても、システムが明示的なリクエストをこっそり覆したことを管理者が知る手段がまったくない、ということはありうる。それをバグと呼ぶか機能の欠落と呼ぶかは捉え方の問題だが、管理者側から見ればその影響は黙った失敗と同じだった。

## 解決 {#resolution}

Neil Hormanの修正は、予約された割り込みのベクタ割り当てを確定させる関数 `activate_reserved()` にチェックを1つ追加する。割り込みの実効アフィニティマスクが、実際に要求されたアフィニティマスクの部分集合でない場合、`pr_warn("irq %u: Affinity broken due to vector space exhaustion.\n", ...)` をログに出すようになった。パッチをメインラインに取り込んだThomas Gleixnerは、自身の役割を「changelogに手を入れ、`pr_warn()` をより有益なものにした」と説明している。根本的な診断と修正はHormanによるものであり、マージ前に再現され修正に対してテストされた報告事例をもとにしていた。

## 教訓 {#what-it-taught-us}

**コードパスが完全に正しくても、挙動を変えたことを観測する手段がなければ、運用者の視点からはバグになりうる。** より広いCPU集合にフォールバックするロジックは間違っていなかった。それが発動したときにログが1行も出ないことこそが本当の問題であり、それを表面化させるには、クラッシュでもテスト失敗でもない、実際に報告された事例が必要だった。

**「情報は技術的にはどこかで入手できる」は「情報が見つけられる」と同じではない。** この欠落が存在した2年間ずっと、`effective_affinity` は真実を告げていた。欠けていたのは、そもそも誰かにそれを見に行かせるきっかけとなるものだった。

!!! warning "注意すべきパターン"
    要求されたものとは異なるリソース（別のCPU、別のメモリノード、別のデバイス）へ黙ってフォールバックするコードパスは、フォールバックのロジック自体が健全であっても、いずれデバッグの罠になる。リクエストが黙って尊重されない可能性があるなら、低いレベルでもよいので一度はログに出すこと。`pr_warn()` 1つのコストは、管理者がどこを見ればよいかわからないコストよりはるかに低い。
